### 2.3 Docker 部署现状（第 21 轮打通，**不要再从零摸索**）

`cd backend && docker compose --profile core up -d --build` 起 **8 个容器**：
`wkagent-app`(8000) / `wkagent-web`(**8080**) / `wkagent-postgres`(5433) /

`wkagent-es`(9201)；`--profile obs` 再加 prometheus/grafana/loki。

**本机 Docker 三个必知前提**：
1. `docker.exe` 在 **`C:\Users\dell\AppData\Local\Programs\DockerDesktop\resources\bin`**
   （不在 `C:\Program Files\Docker`）。DSH 进程的 `$env:PATH` 是旧快照，命令里要先
   `$env:PATH="$bin;$env:PATH"`。
2. 容器命令要访问命名管道，**必须 `danger-full-access`**，`workspace-write` 下必报
   `permission denied ... npipe:////./pipe/dockerDesktopLinuxEngine`。
3. **镜像加速前缀必须写进镜像名**：Docker 29.9.2 上实测 `registry-mirrors` 对
   `docker pull` 不生效。规则见 4.27。

**标准部署 6 步**（顺序不能乱，实测可用）：

## 4. 已踩过的坑（**避免重复踩，全部已修复**）

### 4.1 ⚠️ 最重要：异步桥 `_run_maybe_async`
**症状**：`RuntimeWarning: coroutine 'XxxAsync' was never awaited`，功能静默失效。
**根因**：在**已有运行事件循环**上下文（FastAPI async 端点）里调 `asyncio.run()` 抛
`RuntimeError: asyncio.run() cannot be called from a running event loop`，被外层
`except Exception` 吞掉 → 协程从未执行，功能静默全败。
**实际后果举例**：`POST /kb/reindex` 返回 `total=126 failed=126` 全失败；检索缓存永远不清除。
**修复**：`app/core/asyncbridge.py` 三分支驱动（非 awaitable 原样返回 / 无 loop 用 `asyncio.run` /
**有 loop 用 `threading.Thread` 新开 loop**）。**所有跨同步/异步边界的调用必须走它。**

### 4.2 ⚠️ Alembic `alembic.ini` 不能有非 ASCII
`alembic.ini` 用 locale 编码（本机 GBK）读取，UTF-8 中文注释会报
`UnicodeDecodeError: 'gbk' codec can't decode byte`。**该文件只能写英文**；中文说明放 `alembic/env.py`。

### 4.3 ⚠️ `alembic/script.py.mako` 必须预置 `import app.db.types`
autogenerate 会引用 `JSONType`/`UTCDateTime` 但**不生成对应 import**，漏掉就 `NameError`。模板里已预置。

### 4.4 ⚠️ SQLite 必须手动开外键
`PRAGMA foreign_keys=ON` 默认关闭，外键会被**静默忽略**（级联删除不生效且不报错）。
`app/db/engine.py` 的 `_configure_sqlite` 已挂 connect 事件。测试里建引擎必须用
`make_engine()` 而非裸 `create_engine()`。

### 4.5 ⚠️ 测试必须同时替换 `_ENGINE` 和 `_SESSION_FACTORY`
`session_scope()` 走 `get_session_factory()` 的全局惰性单例，**只换 `_ENGINE` 时工厂仍 bind 旧引擎**，
表现为「导入 126 条但库里有 136 条」（98 条来自开发库）。

### 4.6 ⚠️ 测试不能连开发库
`backend/.local/wkagent.db` 被种子脚本灌过数据，测试连它会导致「跑过种子就红、没跑就绿」的脏失败。
所有 DB 测试用 `tmp_path_factory` 建临时库。

### 4.7 ⚠️ 中文 JSON 被转义成 `\uXXXX`
`JSONType.process_bind_param` 里做 `json.loads(json.dumps(...))` 只是归一化，真正的序列化由底层
`JSON`/`JSONB` 的 `json_serializer` 完成（默认 `ensure_ascii=True` 会再跑一次）。
**唯一注入点是引擎 connect 时替换 `json_serializer`**，已在 `app/db/engine.py` 的 `_patch_json_bind_processors()` 里做。

### 4.8 ⚠️ 脱敏正则的两个坑
1. **地址**：`mask_address` 保留省市区（坐席要靠省市判断时效），只脱门牌。但「省市区」后接
   `**** ` 空格再跟门牌时原正则整体不匹配 → 门牌明文泄漏。已加 `_HOUSE_NO_RE` 二次清除。
2. **姓名误伤**：`满 99 元包邮` → `满 99 元**`。姓氏表含「元」把「元包邮」当人名。已加
   `_NAME_FALSE_POSITIVE_SUFFIX`（83 字）按名字首字判定排除。

### 4.9 ⚠️ `assert_no_pii` 的地址口径
第一版「省+市+区+2 字符」会把已脱敏的 `浙江省杭州市西湖区****` 也判成泄漏 → 业务被堵死。
正确口径：**必须还跟着门牌级信息**（路/街/号/幢/室…）才算完整地址。

### 4.10 ⚠️ RAG 查询改写的同义映射宁少勿滥
`"洗" → ("清洗","洗涤")` 把「能机洗吗」改成「能机清洗吗」，两边都不像。
**验收标准是改写后 query 在库内的字面命中率上升，不是看起来更通顺。** 单字映射一律删掉。

### 4.11 ⚠️ 降级用例前必须清缓存
注入故障组件跑降级断言时，会拿到上一段检查写好的**正常缓存**，用例假红/假绿。
每次注入故障前先 `service.clear_cache()`。

### 4.12 其他小坑
- `ChunkCreateRequest` 的 `knowledge_type`/`category` 在 **`metadata` 子对象**里，放顶层会被 Pydantic 静默忽略
- 内部接口测试必须带 `X-Internal-Token` 头（`conftest.py` 设了 token，不走「本地放行」分支）
- `paginate()` 签名是 `paginate(items, params: PageParams, *, total=None)`，不接受 `page=` 关键字
- 服务层 `list_import_jobs` 返回 **ORM 行**不是 Pydantic 模型，路由里不能 `.model_dump()`

### 4.13 ⚠️ BE-02 分段不能用 `remaining[cut:].strip()`（本轮踩到）
`strip()` 会吃掉切点两侧空白，使 `cut` 语义错位，「拼回去等于原文」断言必失败。
正确写法就是 `remaining[cut:]`——空白留给下一段开头，由发送侧决定是否保留。

### 4.14 ⚠️ 出站幂等键必须带渠道（本轮踩到）
`MessageSendService.idempotency_key` 一开始漏了 channel，测试直接传字符串
`channel="TAOBAO"` 时 `channel.value` 抛
`AttributeError: 'str' object has no attribute 'value'`。
修法：加 `_channel_value` / `_sender_value` / `_msg_type_value` 三个归一助手，
枚举和字符串都能吃。键格式 `outbound:<CHANNEL>:<msg_id>`。

### 4.15 ⚠️ 纯 ASGI 中间件不能在异常路径补发 response.start（本轮踩到）
`ComplianceMaskMiddleware` 里 `except` 分支补发响应会撞 ASGI 框架的
「response.start 已发送」断言。修法：用 `state['streaming']` 标记，
只在 `start` 尚未发出时才补发；`_flush_unmasked` 加 `flushed` 标记防重复发送。

### 4.17 ⚠️ 工具层重试次数口径：`attempts` 不能丢（本轮踩到）
`call_with_retry` 里重试耗尽时抛出的 `MerchantApiError` **不携带 attempts 字段**，
工具层 `except` 分支拿不到「到底试了几次」，`ToolResult.attempts` 恒为 1，
自检脚本的「50401 重试 1+3 次」断言必然假红（实测 `attempts=1`）。
修法：`app/services/tools/base.py` 新增 `_to_api_error(exc, *, attempts=...)` 把尝试次数
挂到异常对象上，并导出 `attempts_of(exc, default)` 读取；
四个工具模块的 `except` 分支统一写 `attempts=attempts_of(exc, attempts)`。
**不改 `MerchantApiError` 的 dataclass 契约**（避免动 12 错误码的公共结构）。
配套口径见 4.19：失败路径断言优先用 `port.calls` 计数。

### 4.18 ⚠️ 脚本化 check 里别用 `MockMerchantToolPort._known` 改数据（本轮踩到）
`MockMerchantToolPort` 的内置 SKU 表是**类级常量**，脚本里 `dict(port._known)` 只是浅拷贝、
改完仍影响后续用例。要造「部分 SKU 不存在」场景请用构造参数
`MockMerchantToolPort(missing_skus={"WK-XXX"})` / `missing_orders={...}`。

### 4.19 ⚠️ 断言 `ToolResult.attempts` 前先确认它在失败路径上有没有值（本轮踩到）
`call_with_retry` 的 attempts 只在**成功**路径可靠；失败时 `result_from_error` 拿到的是
外面 except 的局部变量。**要断言「重试了几次」就用 `port.calls` 计数**（Mock 端口每次调用
都 append 一条），别信 `ToolResult.attempts`。

### 4.20 ⚠️ `model_dump()` 不会序列化 `@property`（本轮踩到）
`OrderQueryResponse.status_cn` / `InventoryItem.status_cn` 是 property，
`model_dump()` / `dict(result.data)` 里**根本没有这个键**，断言 `data["status_cn"]` 必 KeyError。
要验证中文口径，用 `InventoryItem.model_validate(item).status_cn` 把对象 validate 回来再取。

### 4.16 ⚠️ `check_kb_import.py` 原来连的是开发库（本轮踩到）
脚本里 `WK_LOCAL_DB_PATH` 指向 `backend/.local/wkagent.db`（已被种子灌过 336 条），

## 4B. Docker 真机部署阶段踩的坑（第 21 轮新增，**全部只在真实部署暴露**）

### 4.21 ⚠️ `RuntimeError: Event loop is closed`——`asyncio.run()` 与 redis 连接池不兼容
**症状**：`POST /internal/v1/chat/turn` 一律 503 `{"code":30001,"message":"服务暂时不可用"}`。
**堆栈关键帧**（顺序照抄，便于 grep）：
`app/api/v1/chat.py:67 chat_turn` → `app/services/orchestrator.py:521 state = self.store.load(...)`
→ `app/services/session.py:372 raw = _run_maybe_async(self.cache.get(...))`
→ `app/core/asyncbridge.py:66 return asyncio.run(result)`
→ `app/adapters/cache.py:178 return await client.get(key)`
→ `redis/asyncio/connection.py:1095 self._writer.close()`
→ `selector_events.py:864 self._loop.call_soon(...)` → **`RuntimeError: Event loop is closed`**。
**根因**：`asyncio.run()` 每次新建并**关闭**一个 loop；而 `redis.asyncio` 的连接池把 socket
绑在「创建它的那个 loop」上，跨 loop 复用就会在 `transport.close()` 里炸。
**三处修复（缺一不可）**：
1. `app/core/asyncbridge.py` 新增线程本地 loop：`_LOCAL = threading.local()` +
   `_thread_loop()`（`asyncio.new_event_loop()` 缓存，closed 则重建），第三分支由
   `asyncio.run(result)` 改为 `loop = _thread_loop(); return loop.run_until_complete(result)`。
2. `app/adapters/cache.py` 的 `RedisCache` 把 `self._client` 改成 `self._clients: dict[int, Any]`
   （按 `id(loop)` 分桶）+ `self._locks: dict[int, asyncio.Lock]`，`_get_client()` 里
   `loop = asyncio.get_running_loop()` 取桶。
3. `app/adapters/sparse_index.py` 的 `EsSparseIndex` 同样改成 per-loop 客户端字典。
**注意**：不要改回 `asyncio.run`，也不要改成「全局单例 async client」——后者在
gunicorn 多 worker 下同样会跨 loop。

### 4.22 ⚠️ `MilvusVectorStore` 从不创建集合，全新 Milvus 上 336 条全失败
**症状**：`POST /internal/v1/kb/reindex` 返回 `{"total":336,"vectors_indexed":0,"sparse_indexed":0,"failed":336}`，
日志里每条批次都是 `pymilvus.exceptions.DescribeCollectionException: <DescribeCollectionException:
(code=100, message=can't find collection[database=default][collection=wk_knowledge_chunks])>`。
**根因**：适配器只有 `upsert/search/delete/count/health`，**没有任何建集合代码**；
本地开发用 `NumpyVectorStore`（自动建目录），所以从来没人发现。
**修复**：`app/adapters/vector_store.py` 新增 `_ensure_collection(client)`，在 `_get_client()`
里建连后立刻调用；`has_collection()` 先判存在（幂等），再按类 docstring 里那张表建 schema：
`chunk_id VARCHAR(64) 主键 / vector FLOAT_VECTOR(1024) / content VARCHAR(4096) / category VARCHAR(64) /
sku_ids ARRAY(VARCHAR) / knowledge_type VARCHAR(32) / authority INT8 / channel ARRAY(VARCHAR) /
effective_from VARCHAR(16) / version INT16 / enabled BOOL`，索引 `AUTOINDEX` + `COSINE`。
**⚠️ schema 里仍然刻意没有 stock/price 字段**（HC-3 的结构性保证），加字段前先想清楚。

### 4.23 ⚠️ 容器里缺 `aiohttp`，`AsyncElasticsearch` 构造即崩
**症状**：`ValueError: You must have 'aiohttp' installed to use AiohttpHttpNode`
（`elastic_transport/_node/_http_aiohttp.py:84`）。
**根因**：`AsyncElasticsearch` 默认传输层是 AiohttpHttpNode，但 `requirements.txt` 只写了
`elasticsearch`，没写它的异步传输依赖；本地单测全用 `Bm25SparseIndex`，永远走不到。
**修复**：`requirements.txt` 的 ES 段加 `aiohttp>=3.9`（已加注释说明原因）。

### 4.24 ⚠️ `elasticsearch>=8.12` 会装成 9.x 客户端，被 8.13.4 服务端拒收
**症状**：`elasticsearch.BadRequestError(400, 'media_type_header_exception',
'Invalid media-type value on headers [Content-Type, Accept]', Accept version must be either
version 8 or 7, but found 9. Accept=application/vnd.elasticsearch+json; compatible-with=9)`
**根因**：`>=8.12` 不设上界，pip 直接装了 9.x；客户端把 Accept 头写成 `compatible-with=9`。
**修复**：钉成 `elasticsearch>=8.12,<9`。**升级 ES 服务端镜像时必须同步改这个上界。**

### 4.25 ⚠️ pydantic-settings 对 `list[...]` 强制 `json.loads`，逗号分隔会直接启动失败
**症状**：容器启动即 `SettingsError: error parsing value for field "llm_domain_allowlist"`。
**根因**：`.env.example` 里写的是逗号分隔（`WK_LLM_DOMAIN_ALLOWLIST=dashscope.aliyuncs.com,open.bigmodel.cn,...`），
但 pydantic-settings 对 list 字段**在 validator 之前**就做 `json.loads`，所以文件里
已有的 `_split_csv` 校验器**永远轮不到执行**。
**修复**：`from pydantic_settings import NoDecode` + `Annotated[list[...], NoDecode]`，
对 5 个字段全部标注：`cors_origins`、`llm_domain_allowlist`、`image_allowed_formats`、
`ticket_retry_backoff`、`compliance_mask_prefixes`；并把 `_split_csv` 增强为
「空串→[] / `[` 开头→`json.loads` / 否则按逗号切」，validator 列表补上 `ticket_retry_backoff`。
**这个 bug 一直隐藏的原因**：仓库只发 `.env.example`，单测从不加载 `.env` 文件。

### 4.26 ⚠️ `REPO_ROOT` 在容器里算成了 `/`
**症状**：worker 起不来，`ensure_local_dirs()` 建 `/backend/.local` 抛 `PermissionError`；
`/internal/v1/kb/import` 报 `商家材料包缺少必需文件`。
**根因**：`REPO_ROOT = Path(__file__).resolve().parents[3]` 是按宿主机布局
（`<repo>/backend/app/core/config.py`）写的；容器里是 `/app/app/core/config.py`，
`parents[3]` 直接是 `/`。
**修复**：改为 `_detect_repo_root()`——先试 `parents[3]`，若 `(candidate/"backend").is_dir()`
或 `(candidate/"商家材料包").is_dir()` 就用它（宿主机），否则退回 `parents[2]`（容器 `/app`）。
配套：`app/api/v1/kb.py` 的 `_package_dir()` 从 `REPO_ROOT / "商家材料包"` 改为
`get_settings().merchant_package_dir`（受 `WK_MERCHANT_PACKAGE_DIR` 控制）。

### 4.27 ⚠️ compose 的镜像前缀拼接 + MinIO 官方镜像已下架
**症状 A**：`docker compose up` 直接失败，`docker.io/quay.io/coreos/etcd:v3.5.14` 与
`docker.io/docker.elastic.co/elasticsearch/elasticsearch:8.13.4` 这种地址不存在。
**根因**：`docker-compose.yml` 给**所有**镜像都加了 `${REGISTRY_MIRROR:-docker.io}/` 前缀。
**修法**：非 docker.io 仓库**用独立变量、不套前缀**，默认值取国内可用地址 ——
etcd 用 `${ETCD_IMAGE:-quay.m.daocloud.io/coreos/etcd:v3.5.14}`、
ES 用 `${ES_IMAGE:-elastic.m.daocloud.io/elasticsearch/elasticsearch:8.13.4}`
（DaoCloud 前缀替换规则：`quay.io→quay.m.daocloud.io`、`docker.elastic.co→elastic.m.daocloud.io`）。
能直连官方仓库的环境，把两个变量改回 `quay.io/coreos/etcd:v3.5.14` /
`docker.elastic.co/elasticsearch/elasticsearch:8.13.4` 即可，详见 4.32。
**经验**：`registry-mirrors` **只管 docker.io**，把别的站点塞进去是错的；
而且 Docker 29.9.2 上实测 `registry-mirrors` 对 `docker pull` 也不生效，
**必须把加速前缀写进镜像名**。
**症状 B**：`minio/minio:RELEASE.2024-05-28T17-19-04Z` 报 `Error response from daemon: denied`
（换 `docker.1ms.run` / `hub.rat.dev` 则是 `manifest unknown: 官方仓库可能已删除该镜像`）。
**根因**：MinIO 已把镜像从 Docker Hub 撤下，`quay.io/minio/minio` 直接拉也是 `unauthorized`。
**修法**：用社区仍在持续发布的同名镜像 `pgsty/minio`（tag 形态一致），compose 里写成
`image: ${MINIO_IMAGE:-docker.1ms.run/pgsty/minio:RELEASE.2026-08-04T00-00-00Z}`，
并**同时设** `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`（新版必需）与旧的
`MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY`。查可用 tag：
`https://docker.1ms.run/v2/pgsty/minio/tags/list`。

### 4.28 ⚠️ 前端镜像必须用 node ≥22.5（`node:sqlite`）
**症状**：`docker build` 里 `npm run build:only` 失败，
`Error [ERR_UNKNOWN_BUILTIN_MODULE]: No such built-in module: node:sqlite`
（`at ModuleLoader.builtinStrategy`），`failed to load config from /app/vite.config.ts`。
**根因**：`vite.config.ts` / `mock/vite-plugin-bff-mock.ts` 用了 `node:sqlite` 内置模块，
它从 Node 22.5 起才有；本机开发环境是 v24.18.0，而 Dockerfile 一开始写了 `node:20-alpine`。
**修法**：`frontend/Dockerfile` 的 `ARG NODE_IMAGE` 默认值改成 `node:24-alpine`，
compose 里传 `${REGISTRY_MIRROR}/library/node:24-alpine`。

### 4.29 ⚠️ 本地部署别给 Cookie 加 `Secure`
`frontend/deploy/nginx.conf` 里有 `proxy_cookie_path / "/; HttpOnly; SameSite=Lax; Secure";`，
那是**生产 HTTPS** 版本。容器版 `deploy/nginx.docker.conf` **刻意去掉了 `Secure`**——
本地一键部署是 `http://localhost:8080`，加了 Secure 浏览器拒收，表现为
「登录接口 200 但页面立刻又变未登录」。改配置时别把这两份搞混。

### 4.30 ⚠️ `backend/.env` 会泄漏进 pytest，让导入类用例全红
**症状**：`tests/test_kb_api.py` 的 4 个导入用例失败，
`{"code":10004,"message":"源文件不存在：data/FAQ知识库.csv"}`（404），
其余 1107 个全绿。**只在这台机器上红**，换台没 `.env` 的机器就绿。
**根因**：为了 Docker 部署生成的 `backend/.env` 里写着
`WK_MERCHANT_PACKAGE_DIR=/data/商家材料包`（容器路径）；pydantic-settings 会从
**cwd** 读 `.env`，在 Windows 上 `/data/商家材料包` 解析成 `D:\data\商家材料包`（不存在）。
注意 `WK_ENV` 没被污染，因为 `tests/conftest.py` 顶部有
`os.environ.setdefault("WK_ENV", "local")` 先占了位——所以从日志看 `env=local` 很正常，
更容易误判成「不是 .env 的问题」。
**修法**：`tests/conftest.py` 的 autouse 夹具 `_reset_singletons` 里显式
`monkeypatch.setenv("WK_MERCHANT_PACKAGE_DIR", str(Path(__file__).resolve().parents[2] / "商家材料包"))`，
并且要放在 `get_settings.cache_clear()` **之前**（该夹具已有这行）。
**通用原则**：测试必须自洽，**不允许依赖开发机上的 `.env`**。以后凡是新增
「部署时才设」的环境变量，都要在 conftest 里给测试一个确定值。

### 4.31 ⚠️ nginx `add_header` 是覆盖不是继承，index.html 会丢全部安全头
**症状**：`curl -I http://127.0.0.1:8080/` 和 `/index.html` 都**没有** CSP /
`X-Frame-Options` / `X-Content-Type-Options` / `Referrer-Policy`，
但 `/assets/*.js` 有。首页恰恰是最需要 CSP 的文档。
**根因**：nginx 的 `add_header` 在 location 层一旦出现，就**不再继承** server 层的
`add_header`（官方文档：`These directives are inherited from the previous configuration
level if and only if there are no add_header directives defined on the current level.`）。
`location = /index.html` 里原本只有一条 `add_header Cache-Control`，
于是 server 级那 4 条安全头**全部失效**；而 `/` 经 `try_files` 内部跳转到
`location = /index.html`，所以首页也没头。
**修法**：在 `location = /index.html` 里把 4 条安全头**原样重复**一遍
（`deploy/nginx.conf` 与 `deploy/nginx.docker.conf` 两份都要改，已改）。
**排查提示**：以后新增任何带 `add_header` 的 location，都要问一句「server 级那 4 条还生效吗」。

### 4.32 ⚠️ 镜像源被写死进 compose，换个环境就拉不动
**症状**：`docker compose --profile core up -d` 在别的机器（尤其是境外或企业内网）上
直接卡在 `Get "https://registry-1.docker.io/v2/": context deadline exceeded`，
或者报 `docker.io/quay.io/coreos/etcd ... not found`。
**根因**：`_ROOT` 这一层把**国内专用镜像源直接写进了 image 字段**：
`quay.m.daocloud.io/coreos/etcd`、`elastic.m.daocloud.io/...`、
`docker.1ms.run/pgsty/minio`。这些地址只在「国内 + 能连 daocloud」这一个前提下成立；
换到能直连 `quay.io` / `docker.elastic.co` 的环境，反而变成**只有国内能用**。
这与交付物「可交付、可迁移」的目标是矛盾的。
**修法**（已改）：三个非 docker.io 的仓库全部改成可覆盖变量，默认值保持国内可用：
```yaml
image: ${ETCD_IMAGE:-quay.m.daocloud.io/coreos/etcd:v3.5.14}
image: ${ES_IMAGE:-elastic.m.daocloud.io/elasticsearch/elasticsearch:8.13.4}
image: ${MINIO_IMAGE:-docker.1ms.run/pgsty/minio:RELEASE.2026-08-04T00-00-00Z}
```
`.env.example` 里同步补上 `ETCD_IMAGE` / `ES_IMAGE` / `MINIO_IMAGE` / `APT_MIRROR` /
`PIP_INDEX_URL` 五个开关，并注明「出海环境改回官方地址、APT/PIP 留空」。
**验证方式**：`docker compose --profile core config` 分别在不设变量、设官方地址两种情况下
都要 exit=0，且解析出的 image 行随之变化（已实测通过）。

### 4.33 ⚠️ 「镜像源」分三个层次，不能混成一个变量
真机部署时最容易搞混的一点，值得单独记一笔：
| 层次 | 作用对象 | 配置位置 | 本项目取值 |
|---|---|---|---|
| 构建期 apt 源 | `apt-get update`（装 ffmpeg / libpq5） | `Dockerfile` 的 `ARG APT_MIRROR` | `mirrors.aliyun.com` |
| 构建期 pip 源 | `pip install -r requirements.txt` | `Dockerfile` 的 `ARG PIP_INDEX_URL` | 清华源 |
| 运行期基础镜像 | `FROM python:3.11-slim` / `node:24-alpine` | compose build args 的 `PYTHON_IMAGE` / `NODE_IMAGE` | 跟随 `REGISTRY_MIRROR` |
| 运行期业务镜像 | postgres / redis / etcd / minio / milvus / ES | compose 各服务 `image:` | 见 4.32 |
**关键**：`REGISTRY_MIRROR` 只能套在 **docker.io** 的镜像上。给 `quay.io/...` 加前缀会拼成
`docker.io/quay.io/...` 这种不存在的地址（4.32 踩过）。另外 Docker 29 上
`daemon.json` 的 `registry-mirrors` **实测不生效**，只有「镜像名带前缀」才可靠——
所以本项目走的是前缀方案，没依赖 daemon 级镜像加速。

## 6. 关键设计决定（含理由，**不要推翻**）

### 6.1 为什么不用重量级 Agent 框架
任务书 3.1 明确不引入 LangChain/LangGraph 等。理由：三道闸与 6 条转人工规则必须**确定性可控、可测、可审计**。
所以 `orchestrator.py` 是手写的 DAG，每一步都能单测。

### 6.2 为什么 `NO_EVIDENCE` 时返回**空**上下文
`answer_context_from()` 在 `NO_EVIDENCE` 时返回 `[]` 而非低分片段。这是从**源头**杜绝无依据硬答——
调用方拿不到片段，就不可能拼出答案。比「生成后再拦」更可靠。

### 6.3 为什么 RRF 不用加权求和
两路分量纲不同（余弦 ∈[-1,1]，BM25 无上界）。RRF 只用排名，天然无量纲，换 embedding 模型不影响融合逻辑。
`score = Σ 1/(k + rank_i)`，k=60。

### 6.4 为什么检索缓存 TTL 是 120s 而不是 3600s
必须 < `knowledge_effective_delay_minutes * 60`（=300s），否则知识更新后缓存期内查不到，违反 5 分钟生效 DoD。
注意：`answer_cache_ttl_seconds`=3600 是**LLM 答案缓存**，两套东西不要混。

### 6.5 为什么验签失败也返回 200
契约 2.3.4 明确要求。渠道侧看到非 200 会持续重推，一条伪造报文就能把重推队列打爆。
返 200 + 本地丢弃 + **安全告警日志 + Prometheus 指标**。

### 6.6 为什么幂等占位在入队之前
先入队再占位的后果：并发重推时两条都进队列，消费者可能已跑完编排，**重复回复已在用户侧可见**。
先占位把去重成本压到一次 SETNX。

### 6.7 为什么回调端点用 `await request.body()` 而非 Pydantic
验签必须对**原始字节**算 SHA-256。Pydantic 解析后的对象重新序列化会改变字段顺序/空格/转义，
与商家侧算出的摘要不一致，验签 100% 失败。

### 6.8 为什么拼多多适配器要两层解包
PDD 的 `msg` 字段是**字符串化 JSON**，里面 `msg.content` **又是**字符串化 JSON。
这是该平台最常见的解析翻车点。

### 6.9 为什么意图分类用规则 + 词表而不是先上模型
可解释（每命中能打印证据词）、可离线（无 API Key 也能跑通）、可审计。
**不要用评测集去调词表**——那是在拟合噪声。

### 6.10 情绪词的验收标准是误报率不是召回率
把中性用户判成愤怒会触发转人工规则②，代价远高于漏判轻微不满。
已剔除 `还没`/`等了`/`急`/`几天了` 等误报词。

### 6.11 商家语料标注噪声的已知事实
商家把「我要投诉」「12315」「什么破店」统一标成**兜底**（不是售后服务）——这是业务口径，
投诉是「机器人不该自己处理」的典型，必须直通人工。已按此校准词表。

情绪标注相关性极弱（同一句话不同行被标成满意/不满/愤怒），**75.0% 是可辩护的下限**。
真正达标的是 4 条不受标注噪声影响的确定性断言：连续 3 轮负面、正面不误判、强负面词判愤怒、无情绪词判中性。

### 6.12 为什么 BFF 响应**不做**脱敏（`/bff/v1` 不在 mask 前缀里）
`mask_value` 按「12 位数字串」识别订单号，而工单号是 `TS`+12 位，正好命中。加上 `/bff/v1`
之后列表返回 `TS25****9360`，坐席拿它查详情**必然 404**，也无法把工单号回填商家系统——
**脱敏直接废掉坐席的核心动作**。

坐席是内部受控角色，合规靠另外三层保证：`require_role` 角色裁剪（配置写操作要
supervisor/admin）、`app/schemas/bff.py` 字段裁剪（没声明的字段不出网）、`AuditLog`
全量写审计。买家侧出站文本仍由合规闸（BE-17 位置①）与 `/internal/v1/message` 的
脱敏兜住。**这个取舍是刻意的，不要「为了合规」把它加回去。**
